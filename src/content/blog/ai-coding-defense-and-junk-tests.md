最近开发主力切到了 GPT 6 系列，Luna、Astra、6.1 Sol、6.1 Terra 换着跑。用着用着憋了一肚子槽点：这些新模型实在是太喜欢过度防御和刷测试了。有些代码明明写到这里就刚刚好，它非要自作聪明地往下加，最后硬生生把架构和任务范围拉到膨胀。

单看它补的每一行代码，考虑周全、验证充分，听上去都是好事。你很难找到一个不保留它的理由。可当这些东西滚雪球一样堆在一起时，原本半小时能交差的事被无限期拖延，代码量凭空长了一大截。

## 总有“还有一件事”

Hacker News 上的一条评论，有个用 Astra 的老哥（AmazingTurtle）吐槽说，AI 为了确认一个测试确实被修好了，非要反复跑整套测试套件，每轮干等 15 分钟。中间让他做一次 rebase，六个多小时过去还没完事，因为它总能找到“还有一件事”需要去完善。[^hn]

“还有一件事”，这个形容精准得让人苦笑。任务原本有个清晰的终点，但它做着做着，自己把终点线往后挪了。新揪出来的问题里可能确实有值得改的，但全塞进同一个 PR 里，人就只能坐在屏幕前干等。等完还要硬着头皮看大几百行的 diff，逐一判断那些它“顺手做掉”的逻辑到底该留还是该删。

代码里的防御性编程也是这个重灾区。有些校验明明在 API 入口已经做完，进了内部函数，它还要重新判空、检查类型、补默认值。一个原本几行就能说清楚的业务函数，读它之前得先弄明白外围那一圈防御到底在防什么。更糟的是，有时防着防着，连本该暴露的底层错误都被它强行捂死了。比如一个读取失败，它在 `catch` 里贴心地返回个 `[]`，前端页面直接显示“暂无数据”。报错是没了，数据也没了，接下来排查问题还得连环抽丝剥茧。

在这些地方多加一层兜底，并不会让人更省心。调用方得随时防着自己会不会拿到一个莫名其妙的默认值，以后重构的人也得反复推敲这层处理到底能不能删。至于为了一个“未来可能存在”的需求去叠抽象层和兼容性，留下的全都是未来需要阅读和维护的债务。即使生成它们只需要几分钟，维护它们的成本一分钱也省不掉。

## 测试写了很多，测到了什么

在写测试这件事上，AI 更容易让人放松警惕。它啪地生成了一批用例，又全部跑绿了，任谁看都是一个完美的交付结果。但很多时候，这些测试根本没测到点子上。

GitHub 上 [prove-it 这个 Skill](https://github.com/nagi-studio/skills/blob/main/skills/rookie/prove-it/SKILL.md) 的“写测试”章节里直接用了“垃圾测试”这个词。想测数据有没有落库，却转手把数据库操作给 mock 掉，这是“假装在测”；照着现有的输出反向填期望值，连带着错的逻辑一起认账，这是“自己考自己”；业务功能一点没变，只是重构换了个实现方式，测试全崩了，这是“死抠细节”。

里面提供的一个判断标准可以直接拿来用：

> 把它要测的功能故意弄坏，这个测试必须失败；不动功能本身（例如只给内部变量改个名），这个测试必须保持通过。

如果要验证真实的存储逻辑，光看 mock 的保存函数被调用了一次显然是在自我安慰。真把写入那一行删掉，测试到底能不能报警，才是试金石。另一个死循环在于，现在的业务代码和测试用例往往出自同一个模型。如果它一开始就理解错了需求，完全可能用一套错误的实现去配一份完美的错误答案，最后自信满满地告诉你测试 100% 通过。为了审查这些测试，你还得把业务逻辑重新在脑子里人肉跑一遍。

这类垃圾测试留下来，后人重构时只会变成绊脚石。功能完好无损，测试天天报错，人又得陷进去分辨到底是代码坏了还是测试写死了。前面提到 HN 的那条评论还指出了另一种时间黑洞：测试本身也许没错，但为了一个局部的小修改去反复全量跑几千个用例，时间全被耗干了。OpenAI 自己的 Astra 官方文档里也提到了小任务里测试链过长的问题，建议根据改动量来动态决定验证范围，别动不动就重跑全量。[^official]

## 修 bug 时先别扩任务

现在修 bug 的时候，我甚至想在 Agent 指令里加一条死命令：不要顺手新增任何测试。先跑已有的相关测试，然后按照原样复现步骤确认修复即可。原本半小时修完的单点问题，非要额外补一套 mock 和几个极端的边界 case，Code Review 的时候又得多看一堆废话。我实在不想每次报一个 bug，都默认附赠一项“新增回归测试套件”的隐形 KPI。

但把这些要求写进提示词里，往往又会陷入前后互搏的尴尬。“直接做”后面如果跟着一句“绝对不能出错”，你让它到底听哪句？光是把“不要过度设计”、“不要防御”的语气加重，而不说清楚哪些东西是可以接受“不完美”的，AI 依然会迷茫。

## 不要只下禁令

Linux DO 上有个帖子的观点挺有意思，作者发现对 AI 越骂它越容易过度防御，他的建议是“允许犯错，多鼓励肯定，并提供明确参考”。[^encouragement] 按照他的说法，模型之所以拼命防御，是因为“缺乏安全感”。这个词虽然是一种拟人化的形容，但从 Prompt 的角度来看，当系统一直强调“不能出错”时，它确实倾向于用密不透风的检查来保证安全交差。

比起反复在提示词里喊“不要”，给它划定一个“可以偷懒”的边界往往更有用。如果这只是一个本地的临时原型，数据丢了没关系，改动随时能回退，那就把这些上下文明确告诉它。先糙快猛地出一版，不合适再调。或者直接丢给它一段现有的骨干代码，告诉它：“做到这个程度就已经够了，按这个风格接着写。”让简单实现有据可循，给它一个可以安心交付的理由。否则光说一句“禁止过度工程”，你和 AI 对“过度”的定义可能差了十万八千里。

而且，这些条条框框往往不只存在于当前的对话框里。你的 `AGENTS.md` 里可能写着“每次修改必须补齐测试”，别的 Skill 里又卡死“交付前跑完完整套件”。模型越听话、越守规矩，在这些隐形规则上耗费的时间就越多。官方文档也承认 Astra 对这类全局指令文件非常敏感。[^official] 只要这些老规矩还在底座里躺着，你在对话里拼命喊“快一点”、“写简单点”，效果恐怕微乎其微。

我只是希望交给它的那件事，能有一个干脆利落的结束。功能做完，核心检查通过，至于顺手发现的其他边缘问题，另记一笔。下次改不改，那是下一件事了。
