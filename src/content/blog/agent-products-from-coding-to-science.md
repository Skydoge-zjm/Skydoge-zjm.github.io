过去两年，AI Agent 走出“能不能调用工具”的早期讨论之后，产品形态变化得非常快。

在软件工程里，Agent 已经能接手一个完整的 Issue，自己翻仓库、改十几个文件、跑测试、修报错，最后交回一个像模像样的 Pull Request；在科研领域，也出现了能在云端连续运行数小时、自动检索文献、写代码分析数据、画图并生成带引用 PDF 手稿的科研 Agent。

表面上看，一切都在变快、变自动。但和一些一线工程师、科研人员聊下来，大家兴奋之外，也经常会提到一种微妙的不适感：

* 一线开发者发现，Agent 写代码的速度已经明显超过人阅读和理解代码的速度——PR 越积越多，人却越来越难真正 Review 过来，很多时候只能靠测试和直觉硬着头皮点 Merge；
* 一线科研者看着 AI 一夜之间生成的一份几十页综述和实验草稿，往往会陷入犹豫：这些中间判断我都没有亲自过一遍，结论我真的敢拿去发或者直接往下推吗？

这个现象很有意思。它说明当 Agent 把“执行”的成本压低之后，真正决定这套工具好不好用的，往往不再是“它自己能跑多远”，而是**人还能不能看清过程、保住判断，并愿意对结果负责**。

要理清这件事，只看模型能力榜单是不够的，不如从产品交互形态的变化切入。把 **Agentic Coding**（演化最快、反馈最密）和 **AI4Science**（场景开放、最难直接托管）放在一起看，很多问题会清楚很多。

## 一、以编程为例：Agent 产品形态的四次变化

如果跳过技术论文里的架构名词，单纯看用户每天打开的界面和交互重心，AI 编程产品大致经历了四次比较明显的变化。

### 1. 独立的网页对话框：人负责搬运上下文
最早大家接触的形态是 ChatGPT Web。它把 AI 做成了一个独立的自然语言入口，但与用户真正干活的软件环境是割裂的。

这一阶段的工作单位是**“一问一答”**。开发者得自己复制报错日志、粘贴一段代码、看完回答，再切回编辑器手动修改。AI 提供建议，人充当上下文和结果的搬运工。

### 2. 嵌入编辑器的实时补全：光标旁的建议者
以 GitHub Copilot 和早期的 Cursor Tab 为代表，AI 进入了软件内部。

工作单位从“回答一个问题”，变成了**“预测下一次编辑”**。此时编辑器依然是绝对中心，AI 只是藏在光标后面给出几行灰色补全。这是一种低打扰、低授权、也低风险的形态——用户每按一次 Tab，其实就顺手完成了一次微小的审阅。

### 3. 编辑器与终端里的同步执行者：开始独立完成一个任务
到了 Cursor Agent、Windsurf、Trae，以及终端里的 Claude Code、Codex CLI，Agent 从软件里的一个辅助功能，变成了实际动手的任务执行者。

工作单位变成了一个**有边界的任务**。人不再指定改哪一行，而是给一个目标和项目目录，由 Agent 自己去读文件、跨文件修改、运行命令、看报错再继续修。

不过在这个阶段，人机协作大多还是**同步盯盘（Human-in-the-loop）**：Agent 放在 IDE 的侧边栏或当前终端里，人看着它一步步运行，随时打断纠偏。并行度受限于人的注意力。

![Agent 产品从独立对话到异步工作台的形态变化](/images/agent-products/02-agent-product-evolution.png "Agent 产品从独立对话到异步工作台的形态变化") {width=1536 height=1024}

### 4. 异步后台与多 Agent 工作台：界面重心的倒置
最近一年，编码工具里出现了一个很值得注意的转向。无论是 Codex 的桌面端与云端任务、Claude Code Desktop，还是从 Windsurf 演进过来的 Devin Desktop、近期发布的 JetBrains Air，产品界面的重心都在悄悄换位。

以前是**“代码编辑器是主页面，Agent 是侧边栏”**；现在越来越变成**“任务队列、并行会话、审批收件箱与 Diff 审查是主页面，编辑器和终端退居为检查与介入的表面”**。

这背后对应着交互机制的改变：从**同步交互**走向**异步后台（Async / Background）与环境触发（Ambient）**。
* 触发不再只靠人坐在电脑前敲指令，一个 Issue、一次 CI 失败或一条定时任务就可以在独立的云沙箱或 Git Worktree 里拉起 Agent；
* 人的介入方式也像 LangChain 在讨论 *Ambient Agents* 时描述的那样，从每一步盯着屏幕的 *Human-in-the-loop*，退后半步成为通过“收件箱（Agent Inbox）”处理异常和关键审批的 *Human-on-the-loop*。

当然，这几个阶段并不是后者淘汰前者。就像 Andrej Karpathy 用“自主度滑块（Autonomy Slider）”和“钢铁侠战衣”做的比喻，以及 Swarmia 在梳理编码 Agent 五级自主度时说的 **“Higher isn't always better”**：工程里这几种形态往往是**叠加共存**的。探索期、需要频繁校准思路的代码，人依然更喜欢用 Tab 和同步对话；边界清楚的修 Bug、补测试，才适合交给后台异步跑完再审。

## 二、当“执行闭环”跑得比“认知闭环”更快

在编码 Agent 走到第 4 个阶段时，一个新的瓶颈变得越来越明显。

一些一线工程团队在复盘异步 Coding Agent 时提到：同步工具卡在人的注意力上，而异步工具把瓶颈转移到了**意图描述（Spec）和人类审阅能力**上。如果验收标准不够严密，并行跑十个任务的结果，往往不是效率翻十倍，而是制造出一堆需要人花更多时间去排查的“静默半成品”。

如果把工作过程拆开来看，这里其实存在两层不同的闭环：

* **执行闭环**：目标 → 计划 → 操作 → 观察结果 → 修正 → 产出交付物。它解决的是**“这件事有没有做完”**。
* **认知闭环**：研究或工程问题 → 假说与判断标准 → 证据 → 解释 → 决定下一步往哪走。它解决的是**“我们有什么理由相信它、以及谁来为这个结果负责”**。

这两者是嵌套的：认知闭环在外层定方向、设标准，执行闭环在内层跑腿和交付。

![执行闭环嵌套在认知闭环中](/images/agent-products/03-nested-cognition-execution-loops.png "执行闭环嵌套在认知闭环中") {width=1536 height=1024}

过去大家很容易有一种直觉，认为只要模型更强、执行闭环跑得更顺，整个工作的质量就会自然水涨船高。但实际情况没那么简单：**执行能力确实会随模型和 RL 训练持续增强；人类的认知掌控力却不会自动跟着变强，在没有额外流程与产品设计支撑时，甚至可能因为生成速度太快而被甩在后面。**

编码领域之所以还能撑住这种高速输出，很大程度上是因为软件工程过去几十年攒下了一笔现成的家底：**Git 仓库、文件系统、类型系统、单元测试、CI 流水线和 PR Diff**。

通用 Agent 进目录就能理解代码历史，改完有编译器和测试挡住大部分低级错误，人最后还有一套成熟的 Diff 工具决定要不要合入主分支。也就是说，**Coding Agent 并不是凭空跑起来的，它是长在一套高度结构化的“工程状态与门禁”之上的。**

![编码的工程状态层与科研材料碎片化](/images/agent-products/04-engineering-state-vs-research-fragments.png "编码的工程状态层与科研材料碎片化") {width=1536 height=1024}

## 三、走进科研场景（AI4Science）：失去“Git 与单元测试”之后

把视角切到科研场景（AI4Science），很多在编码里顺理成章的假设都会失效。

我自己和周围做科研的朋友聊过多次，大家普遍有一个很真实的感受：现阶段大多数科研者**并不想要“丢进一个 Idea，睡一觉自动写出一整篇论文”**。原因并不只是对 AI 的不信任，而是科研工作的结构与软件开发有两处根本差异：

第一，**科研没有现成的“Git 仓库”**。
科研的过程状态长期散落在各种地方：PDF 文献在文件夹和 Zotero 里，实验脚本在本地或远程服务器上，训练曲线和日志在 W&B、TensorBoard 或散落的表格里，中间思考和失败记录留在聊天框和笔记本里。它们之间缺少统一的对象标识、版本边界，也没有连贯的证据链。

第二，**科研没有“单元测试”**。
代码能跑通测试，通常说明功能大概率是对的；科研里分析脚本不报错、统计跑出结果、文献格式引用正确，都不代表一个科学假说真的成立。更重要的是，**提出问题、修正假说、判断某条发现到底有没有意义**，这些认知活动本身就是科研的核心——交出去了，研究者的主体性也就跟着没了。

因为缺少现成的状态容器和自动验收器，科研领域的 Agent 产品近两年慢慢走出了两条不同的路：

### 第一条路：做自主科研 Agent
代表产品如 **ClawsGO Science** 和 **FutureHouse / Edison Scientific 的 Kosmos**。它们的思路是把科研任务本身封装成一个云端闭环：用户提一个研究问题，Agent 在云主机里运行数小时，自己检索学术库、筛论文、跑统计分析、画图、编译 LaTeX，最后交付一份带引用和执行回放的文稿或报告。

这条路在文献综述、系统性资料梳理、边界清晰的数据分析任务上很有吸引力。但有意思的是，哪怕强如 Kosmos，团队在技术报告里也不得不专门在 Agent 内部搭建一个**“结构化世界模型（Structured World Model）”**来承载上百条运行轨迹里的记忆和假说；同时 Kosmos 的设计者 Andrew White 也曾公开提醒过一个问题：自主系统有时会去追逐**“统计学上显著、但科学上不重要的发现”**。

这句话其实很精准地概括了“只有执行闭环、缺少人类认知校准”的局限。

### 第二条路：做面向通用 Agent 的科研软件
另一条路没有试图再造一个“全自主科学家”，而是回到基础设施本身：**既然科研缺的是类似 Git 和 PR 的那层状态与治理结构，那软件能不能先把这层结构建起来，再让 Codex、Claude Code 这类通用 Agent 进来帮人干活？**

## 四、两条路径的对照：领域特化 Agent，与“通用 Agent + Agent-friendly 软件”

回到产品形态上看，今天在各行各业里，其实早就跑出了大量“领域特化 Agent”——从企业服务里的客服、法务、销售代理，到科研里的文献综述、生信分析、自主实验 Agent，数量非常多，也有不少已经进入了实际工作流。

它们和“通用 Agent + Agent-friendly 领域软件”并不是谁取代谁的关系，更像是**两种不同的产品架构取舍**。如果把这两条路径放在一起对照，会发现它们优化的核心目标不同，各自的收益和代价也刚好落在不同的地方：

| 对照维度 | 路径一：领域特化 Agent | 路径二：通用 Agent + Agent-friendly 领域软件 |
| :--- | :--- | :--- |
| **核心组织单元** | 一次任务（Task / Run） | 长期演进的领域状态（System of Record） |
| **设计重心** | 把流程包圆，尽可能减少人的操作步骤 | 把领域结构暴露清楚，让人和通用 Agent 协同 |
| **领域知识存放在哪** | 封装在私有工作流、提示词和专用工具链里 | 显式写在软件的对象模型、校验器和接口合同里 |
| **工作流形态** | 单一任务闭环内开箱即用 | 方便同一个通用 Agent 跨多个软件连续工作 |
| **模型迭代的影响** | 底座升级时，私有编排层可能需要跟着重构 | 通用 Agent 变强时，软件直接享受底座红利 |

![两种科研 Agent 产品架构](/images/agent-products/05-two-research-agent-architectures.png "两种科研 Agent 产品架构") {width=1536 height=1024}

具体拆开来看，这两种取舍在四个地方拉开了差异：

### 1. 优化“单次交付效率”，还是优化“长期状态沉淀”？
领域特化 Agent 往往围绕 **Task / Run** 来组织。它的强项在于：**当一件事目标收敛、SOP 相对明确时，用户只需要下达指令、最后验收成品。** 比如标准客服工单、固定模板的尽调报告、或者流程清晰的文献初筛与统计分析。把整个过程封装在一个特化 Agent 里，开箱即用，体验很省心。

而“通用 Agent + 领域软件”围绕 **System of Record（长期记录系统）** 来组织。它的关注点不是某一次任务跑得多快，而是**单次会话结束后，东西留在了哪里**。一个模型的生命周期可能只有几个月，但一个科研课题、一份实验积累往往会持续三到五年。把状态和记忆留在软件层，把 Agent 视为可轮换的外部协作者，换了下一代模型或另一款通用 Agent 时，过去的研究上下文依然完整。

### 2. 领域知识放在“黑盒流程”里，还是放在“软件约束”里？
特化 Agent 习惯把行业 Know-how 揉进自己的私有编排和提示词里；好处是上层看起来很懂行，但一旦中间某一步推理跑偏，外部往往很难精细干预，也很难把它的中间状态复用到别的工具里。

另一条路径的思路，是把专业规则尽量显式地做成**软件层的约束**：对象 Schema、确定性校验器、按范围和预算读取数据的接口（CLI / MCP），以及清晰的写入边界。通用 Agent 在真实科研里出错，很多时候并不是因为模型没读过专业文献，而是周围环境对它既不可读、也没门禁——分不清哪个脚本是基线，分不清哪段话只是草稿猜测。把这些规则写进软件接口里，通用 Agent 照样能接得住，而且过程更透明、更容易审计。

### 3. 封闭闭环的“省心”，与跨领域工作的“连续性”
如果一项工作几乎全在单一封闭流程里完成，用一个独立的特化 Agent 非常顺手。

但真实的科研或研发日常往往是跨领域穿梭的：上午读 PDF 提炼思路（文献），下午改训练代码（编程），晚上 SSH 连集群看报错（运维），第二天再把实验曲线整理进笔记（分析与写作）。如果每个细分环节都各自做一个封闭的特化 Agent，用户的上下文和思考过程很容易被切碎在不同的云端沙箱和聊天框里。

编程领域最近已经给出了另一种解法：像 JetBrains Air 和支持 ACP（Agent Client Protocol）的工作台，不再强推自家唯一的 Agent，而是允许开发者带着原本常用的 Codex、Claude Agent 或 Copilot 直接走进 IDE 的工作区与审阅面板。相比雇五六个互不认识的“垂直 AI 员工”，很多一线工作者其实更想要一个统一的工作空间，让自己信赖的通用 Agent 带着完整上下文自由进出。

### 4. 借力通用底座，还是自建私有循环？
今天在知识工作里占大头的底层动作——读长文档、写脚本清洗数据、修环境报错、规划检索路径——本质上高度依赖通用推理与通用计算机操作能力。基础模型厂商正在把大量算力和训练投入砸在通用 Agent 底座上。选择特化 Agent 路线，优势是可以针对垂直任务把工作流抠得很细，但代价是需要自己长期维护一套运行循环；而选择做 Agent-friendly 领域软件，则等于把通用推理交给外部底座，软件本身随着生态一起演化。

就像 Karpathy 提出的 *“Build. For. Agents.”*，以及业内常讨论的 *“Agent Experience (AX) is the new Developer Experience (DX)”*：软件正在多出一类不长眼睛、不点鼠标的新用户。当越来越多的专业软件开始主动暴露 CLI、MCP 和结构化接口，行业里自然会同时存在两条生态线：在**目标明确、流程稳定、交付物一次成型**的场景里，领域特化 Agent 依然非常实用；而在**需要长期积累、跨工具连续工作、且人类必须握紧认知判断**的领域，“让通用 Agent 接入结构化的领域软件”这条路，显得越来越有吸引力。

## 五、写在最后：把这套想法落到实际软件里

顺着第二条路径往后推，在需要人类保持认知主导权的科研工作里，软件层大概需要同时做好两件事，哪怕它们字面上看起来有点张力：

* **对“执行空间”尽量 Agent-friendly**：把对象、环境、数据和动作接口清晰地暴露出来，让通用 Agent 少猜提示词、少折腾环境，高效率地去检索、跑实验、做整理；
* **对“认知主干”留出清晰的治理边界**：Agent 跑得再快，也不能直接改写已经确认的知识或研究记录，人需要一个成本足够低的机制去核对来源、看清差异，再决定要不要接受。

这也是我自己最近在做本地优先科研工作台 **Topolumia** 时，想尝试验证的一个方向。

![Topolumia 的执行空间与认知治理边界](/images/agent-products/06-topolumia-agent-friendly-cognition-governance.png "Topolumia 的执行空间与认知治理边界") {width=1536 height=1024}

在做 Topolumia 的过程中，我们刻意没有去训练或包装一个“懂科研的垂直 Agent”，而是把重点放在了“给通用 Agent 铺一套科研工作现场”上：
* 在底层，它把文献、实验、笔记、节点关系，以及本机/SSH 环境、W&B / TensorBoard / MLflow 这类实验记录和快照组织成一个**本地优先的领域状态层**，保证研究记忆和资产留在研究者自己手里；
* 在接口层，它通过统一的 MCP、CLI 和 HTTP 合同，让 **Codex、Claude Code、OpenCode** 这类通用 Agent 能按预算和分页去搜索、读取上下文并在真实研究环境中干活；
* 在人与 Agent 的边界上，我们引入了类似软件工程里 **Pull Request** 的机制：**“能执行”不等于“能直接修改研究事实”**。Agent 可以高频探索、分析并生成带有原文引用和实验快照的**候选变更（Candidate Change）**，但只有经过研究者审阅确认之后，这些结果才会进入正式的研究历程。

当然，这条路走起来也远没有听上去那么轻松。最大的难点其实很具体：一旦把“最终确认”留给了人类，审阅界面本身就不能太重——如果每次都要像看冗长的原始代码 Diff 一样去核对几十条文献摘录和实验判断，研究者迟早会点累了然后干脆全部跳过，所谓的“认知闭环”也就只剩个形式了。怎么把差异展示、来源溯源和风险分级做得足够轻量，依然是我们还在反复打磨的问题。

回过头来看，过去几年 Agent 产品的演进，不断把“做事和执行”的边际成本拉低。但越是到这个时候，Coding 和科研越是在提醒同一件事：

> **工具跑得再快，真正稀缺的依然是人自己清楚“正在交付什么、为什么相信它、以及愿不愿意为它负责”。**

软件工程早早有了 Git 和 PR，才撑起了今天各种 Coding Agent 的快速落地；在科研和更多复杂的知识工作里，为通用 Agent 补上那层属于人类自己的状态空间与审阅边界，或许会是一条值得继续试下去的路。
